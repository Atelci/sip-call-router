How to use

A tiny contact-center call router: callers dial in over SIP, Java routes each call to an agent with the right skill, and all routing state lives in Redis. Everything on this page updates live.

1. Start some calls

The Call generator starts simulated callers inside the app. Each one is a real SIP client sending UDP packets to port 5060, exactly like an external phone or callgen.py.

Callers
how many calls to place (1–50)
Seconds between
gap between new callers; 0.1 makes a burst
Talk min / max
a connected caller talks for a random time in this range, then hangs up (BYE)
Patience
a queued caller gives up (CANCEL) after this many seconds
Dial
each caller dials one of the ticked users at random. The dialed user is the skill: sip:billing@router needs a billing agent; support means any agent
2. Read the SIP diagram

Each card is one call. The left line is the caller, the right line is the router. Requests go left → right and responses come back right → left. The newest message is at the bottom, with the time since the INVITE on the left.

request from the caller (INVITE, ACK, BYE, CANCEL) 1xx provisional: still working on it 2xx success 4xx failure: rejected or cancelled
INVITE
caller wants to start a call
100 Trying
router got it; stops the caller retransmitting over UDP
182 Queued
no free agent with the skill; pos N is the place in line
180 Ringing
an agent was claimed for this call
200 OK
connected; the small text is the agent (header X-Agent-Id)
ACK
caller confirms the 200 OK: the INVITE / 200 OK / ACK handshake is complete
BYE, 200 OK
caller hangs up; the agent is freed and takes the next waiting call
486 Busy Here
the queue for that skill is full
CANCEL
caller gave up while queued: 200 OK for the CANCEL, then 487 for the INVITE

Click any arrow to see the full message. Worth a look: Via (with rport), the From / To tags (they identify the dialog), Call-ID, CSeq, and our own X-Queue-Position / X-Agent-Id.

The ACK after a 486/487 isn't drawn: the SIP stack absorbs it inside the INVITE transaction before our code sees it.

3. Queues, calls and agents
  • There is one FIFO queue per skill, plus general. The bar shows how full a queue is against max-queue-size; the chips are the waiting callers in order, with a live wait time.
  • A new call goes to the longest-idle free agent with the skill. If there is none, it waits in that skill's queue. If the queue is full, it gets 486.
  • When an agent frees up, it takes the longest-waiting call it can handle, across all its skills.
  • Agent dots: green = available, amber = busy (on a call), grey = offline. alice en, billing, bob en, carol de, billing.
  • Claiming an agent is one atomic Redis Lua script, so two router instances can't hand out the same agent twice.
4. Try these scenarios
Normal day

10 mixed callers: some connect at once, some queue and connect as agents free up.

Queue overflow → 486

A burst of 20 general calls with long talks fills the general queue (max 5); the rest are rejected.

Impatient callers → CANCEL / 487

Only carol speaks German. With 3s patience, the later de callers hang up while queued.

Skill beats idle time

Billing calls only go to alice and carol. bob stays free even though billing callers are waiting.

5. Change agents (terminal)

Take bob offline, then send the same call with AVAILABLE. He picks up a waiting call immediately:

curl -X POST localhost:8080/api/agents/bob/status -H 'Content-Type: application/json' -d '{"status":"OFFLINE"}'

Add a new German agent, then make dave AVAILABLE the same way:

curl -X POST "localhost:8080/api/agents/dave?skills=de"

6. Under the hood
  • The page listens to /api/events (Server-Sent Events). call events come from the Redis channel call-events, sip events from sip-messages, so the page sees the calls of every app instance.
  • The panels re-read /api/stats, /api/queue, /api/calls/active and /api/agents after each event.
  • A call's SIP history is the Redis list sip:{callId} (kept for 1h), so a page opened mid-call still shows the earlier messages.
  • Watch Redis directly: redis-cli MONITOR, redis-cli SUBSCRIBE call-events, redis-cli LRANGE queue:calls 0 -1.
  • App log: the app also writes its log to logs/sip-call-router.log. A small tailer reads what was appended every half second (like tail -f) and sends new lines as SSE event log; /api/logs gives the last 500 lines to a freshly opened page. Type in the filter to keep only matching lines (try a call id or WARN); scrolling up pauses follow.
  • Signaling only: there is no audio (RTP), and the 200 OK carries no SDP.
